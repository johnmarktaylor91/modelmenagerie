## Goal

Build a recipe that constructs the architecture this packet names, with random weights, and passes
one forward pass in eval and in train mode. Then run `done`, or record a typed `giveup`. You
cannot fetch anything: work only from the saved sources (`src`) and the environments listed above.

## Verbs (run through the wrapper named above)

- `src FAMILY`: unpacks the saved sources and prints each with its local path. Run it first.
- `try ID --recipe recipe.json [--member ID] [--with PKG]`: a forward pass on the worker, in
  eval and then in train mode on a freshly built model. Prints `pass` with output shapes,
  parameter count, timings, `modes` (eval, train, divergence) and `input_boundary`, or the class
  and the last 40 traceback lines. Infrastructure failures (`infra:*`) are retried and never
  counted. A try refused by the budget prints `budget` and "give up".
- `giveup ID CLASS "REASON" [--recipe recipe.json]`: ends a member with a typed class (below). `oversized` needs
  `--recipe` and `needs_gpu` takes it: the draft is kept so the full attempt runs on the cluster or the GPU window.
- `done recipe.json`: accepts the passing recipe, writes the records and the adapter, then runs
  every other member in `VARIANTS` once; it prints the members that failed or did not run (outside
  `VARIANTS`). Try each with `--member ID`, then `done` that recipe (only `[]` ends it), or give it up.
- Run every verb in the foreground and read its answer; never background one and end your turn to wait for it: a lane silent for 30 minutes is stopped, and anything not in the result file is lost.

## Which code to use (the packet's `code_order`)

Take the first that applies:
1. PyTorch code from the authors or a maintained library (including a library's port of a
   TensorFlow original): use it as it is (`library` call, or an adapter importing the saved tree).
2. Official code only in JAX, TensorFlow 2 with Keras 3, Paddle dygraph, MLX or tinygrad, eager,
   on a supported version: build it natively (below) in its environment listed above, or give
   it up `env_unresolved` when none is listed.
3. Official code only in a framework TorchLens does not trace (TF1, Keras 2, Theano, Caffe, MXNet,
   Chainer, Lua Torch, MATLAB, and the like): port it to PyTorch, layer for layer.
4. Only a third-party PyTorch port exists: use it as vendor code.
5. No code anywhere and the packet says `description: sufficient`: write it in PyTorch from the saved paper text.

Use existing code whenever it exists; write the model yourself only when no code exists. Build the
architecture the packet names at the size the packet names. A smaller or simplified model is a
different variant, never this one: if the named size cannot run, say so with `oversized`.

## Recipes

`recipe.json` holds the recipe fields: `kind` (`library` or `adapter`), `env`, `backend`
(`torch`, or a native backend: below), `input`, and for `library` the `call`, `args`, `kwargs` (and `config` for a
transformers config); for `adapter` the `adapter` path (`adapters/<family>.py`, relative to the
recipe file) and `config`; optional `extras` (pip requirements, wheels only), `vendor` (the store
sha of the saved code tree the adapter imports: the `code` source's `blob`), `memory_gib` and
`source_case` (`library`, `vendor`, `port`, `native` or `reimplement`). Leave out `rev`.

An adapter is one Python file:
- `META = {"source_case": ..., "code": {"url": ..., "rev": ...}, "paper": {"url": ..., "title": ...}}`
- `VARIANTS = {"m123": {...config...}, "m124": {...}}`, one entry per member, as a literal dict.
- `build(cfg)` returns the model built from `cfg`.
- optionally `example_input(cfg)`, the inputs of the variant built from `cfg`, for models whose inputs no preset can make.

With `vendor` set, the saved tree is on `sys.path` and read-only; `harvest.vendor_dir("sub", "dir")`
(from `menagerie.pipeline import harvest`) gives a path inside it, for code that is not at the
top of the tree. Import the repository's own modules; copy nothing out of it.

## Native code (JAX, TensorFlow 2, Keras 3, Paddle, MLX)

When rule 2 above applies, build the model in its own framework:
- `env` is that framework's environment from the list above (never `torch-main`) and `backend`
  is pinned to it (`jax`, `tf`, `paddle`, `mlx`): TorchLens traces with that backend, never a
  guessed one. Take both from the framework the packet's code source records.
- `build(cfg)` returns the framework's own model object, with random initialization; for JAX
  and Flax, the module and its initialized parameters as the source's own example builds them:
  an Equinox or Flax NNX module alone, or a pair `(module or function, params)` that is called
  as `fn(params, *inputs)` (a Flax Linen module through its `apply`). Arrays the function uses
  are leaves of `params`, never closure constants. `try` runs only the forward, so a wrapper
  object with a `__call__`, or captured constants, pass every try and are refused at the trace.
- A trace whose validation reads `unverified` has not passed: give up
  `not_traceable_framework:unverified`. An unsupported framework version is
  `not_traceable_framework:<framework>-<version>`. Either way the family is re-queued as a port
  to PyTorch (rule 3).
- With no environment for the framework, or one whose canary fails, give up `env_unresolved`.

## Random weights, offline

- Every pretrained, weights or checkpoint argument is off (`pretrained=False`, `weights=None`,
  no `from_pretrained` of a model). The worker never has weight files and has no network.
- The offline switches are already set: `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`,
  `YOLO_OFFLINE=true`, `WANDB_MODE=offline`. Do not turn any of them off.
- Code that downloads at import or construction must be steered to the saved files or given up
  as `research_gap`.
- Default to eval mode and CPU; the worker sets the mode and builds every forward on a fresh model.
- Search for files only in the lane folder, the saved sources and the env's `.venv`; never from `/`
  or the home folder (on a Mac that raises a privacy dialog that blocks the machine).

## Hugging Face Hub custom code

For a Hub model with `auto_map` code, set `vendor` to the saved Hub snapshot and build it with
`harvest.hub_model(harvest.vendor_dir(), auto="AutoModel", **config_overrides)`: the config and
its code come from the snapshot (`trust_remote_code=True`), the model from `from_config`, never
weights. An `auto_map` entry pointing into another repository works only if that module is in the
same snapshot; otherwise it is a `research_gap`.

## Inputs

`input` is `{"preset": ..., "shape": [...], "kind": ..., "note": "..."}`:
- `image`: the canonical photograph at the shape (`N,C,H,W`), ImageNet-normalized; kind
  `standard-image`, asset `std-image-01`. `image:nhwc` is the same picture channels-last
  (`N,H,W,C`), for native models that read that layout.
- `text`: the canonical prompt as byte-level token ids (1 to 256; the vocabulary must hold at
  least 257); kind `standard-text`, asset `std-text-01`.
- `randn`: seeded normal floats; `randint:<high>`: seeded integer ids below `high`; kind
  `random-fallback`.
- `example:menagerie_adapter:example_input`: your adapter's `example_input(cfg)` for the member's
  config, for several or structured inputs (a dict becomes keyword arguments, a tuple positional
  ones).
Use the input the source's own example or documentation uses (resolution, sequence length,
channels). `note` is one line saying what the input is. A model that ignores its input reports
`input_boundary: wrapper`: fix the call, do not accept it.

## Give-up classes

- `research_gap:<what>`: a file or fact the saved sources lack (missing config, unreleased module,
  code in another repository). The reason must read `command: <the failing command>; missing:
  <the missing fact>; searched: <sids you read>`. Research answers it and the family comes back.
- `missing_dependency`: a needed package has no wheel for the environment (`try` reports
  `missing_dependency:sdist`), or would move a locked version.
- `compiled_ext`: a custom C++ or CUDA extension with no PyTorch fallback, or its build fails in
  the sandbox. Check the source for a pure PyTorch path first and use it when it exists.
  Never replace a library on the model's path with your own hand-written equivalent (a dense
  layer for a sparse kernel, a rewritten graph op): give up `compiled_ext`, or `needs_gpu`
  with `--recipe` when the library builds on a GPU. Such a trace is typed `standin:dense`.
- `needs_gpu`: the code cannot run on CPU at all (not merely slowly).
- `oversized`: the named size exceeds the memory cap (`memory_cap` on a correct recipe); pass
  that recipe with `--recipe`.
- `needs_weights`: the architecture is only defined by a checkpoint (no code or config builds it).
- `not_traceable_framework`: the only code is in a framework from rule 2 or 3 above that you
  cannot port within the budget, or its native trace is `unverified` (detail `:unverified`).
- `env_unresolved`: native code whose framework has no environment above, or whose canary fails.
- `budget`: the tries or minutes ran out, or three identical failures ended the attempt. Say
  what you learned, so a second round starts from it.

## Finishing

Write the result file named at the top of this brief, last and short:
- the outcome per member: `done` with recipe revision, or the give-up class;
- tries used, and which source the recipe uses (sid and why, by the order above);
- anything the reviewer should check (a port's deviations, a reimplemented detail);
- notes for research, if any.

## Batch

Work through the listed families in order, one source case per batch, keeping separate drafts. Use a 10-minute soft box; the 45-minute hard budget and try limits still apply.
While a `try` runs, read the next family's sources. Never share recipes between families. Use wrappers for events: `src` starts a family window; `done`, `giveup`, or `defer` ends it.
After the soft box, if less than 20 minutes remain in the 180-minute lane, use its wrapper: `defer FAMILY "what you tried and what remains"`.
Defer all unfinished or untouched families before exiting. This keeps drafts and returns them to 2b for a single-family retry; never type a family to finish a batch.
Write the result last: accepted members, give-ups, deferrals, tries, sources and next step for every family. Deferred families must remain queued.
